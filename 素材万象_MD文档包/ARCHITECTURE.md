# 素材万象｜ARCHITECTURE.md

> 这是素材万象“当前阶段”的推荐结构。
>
> 它不是永久不可修改的规定。
>
> 如果真实开发证明某个设计没必要，可以简化。

# 1. 项目现在到底要做什么

当前不做完整“素材万象”软件。

第一阶段只做三个独立 Skill：

```text
Skill 1：换品
Skill 2：声音克隆
Skill 3：换口型
```

开发完成后，先自己内部使用。

主要使用方式：

```text
WorkBuddy
↓
调用 Skill
↓
Skill 自动调用对应模型
↓
返回结果
```

Codex 在这里的作用只是：

> 帮我写代码、改代码、测试代码。

Codex 不是素材万象最终产品里的工作 Agent。

---

# 2. 第一阶段最重要的目标

不是“架构先进”。

而是：

```text
好用
稳定
调用简单
方便继续改
以后还能套壳
```

所以第一阶段不追求复杂平台。

---

# 3. 每个 Skill 对用户应该是什么体验

## 换品 Skill

用户输入：

```text
原视频
+
新商品图
+
用户换品提示词
```

Skill 自动完成：

```text
读取预设 API Key
↓
使用默认 Gemini Omni Flash 视频模型
↓
把用户提示词与最小保真约束合并
↓
上传原视频并绑定新商品参考图
↓
直接编辑并生成换品视频
```

用户不需要：

- 每次输入 API Key
- 每次选择模型

换品第一版的提示词由用户输入，并且是必填项。

### 换品输入辅助：产品图片分析与预处理 Skill

这是 Phase 1 的输入质量保障，不是新的产品功能：

```text
用户产品原图
↓
默认 DeepSeek 视觉模型检查
├─ 合格：原图直接返回
└─ 不合格：默认 Seedream 生成一次无中文多视角棚拍图
             ↓
           DeepSeek 复检
             ├─ 合格：返回生成图
             └─ 不合格：保留候选图并停止
```

视觉模型和生图模型都通过注册表与适配器选择。独立调用 Skill 时用户可选模型；素材万象以后接入时使用产品默认模型。不得自动付费重试。

---


# 4. “Skill 不绑定模型”到底是什么意思

不是说：

> 每次调用都让用户选模型。

而是：

> Skill 可以有默认模型，但未来应该比较容易换。

例如换品 Skill：

```text
默认模型：gemini-omni-flash-preview
```

平时直接用。

未来如果发现新模型更好：

```text
把默认模型换掉
```

而不是重写整个 Skill。

第一版可以很简单：

```text
Skill
↓
默认模型配置
↓
模型 API
```

如果以后多个 Skill 共用很多模型，再考虑把模型调用抽成更统一的一层。

不要现在就为了“未来可能需要”做复杂系统。

---

# 5. API Key 怎么处理

## 第一阶段

最简单方案：

```text
.env
```

例如：

```text
GOOGLE_API_KEY=xxx
ELEVENLABS_API_KEY=xxx
```

Key 输入一次即可。

以后调用 Skill 自动读取。

用户不需要每次重新输入。

真正的 Key：

- 不写进代码
- 不提交 Git

---

## 未来产品化以后

可能变成：

```text
平台自己的 API Key
```

或者：

```text
每个用户自己的 API Key
```

到真正套壳时再处理。

现在不提前开发复杂 Key 管理系统。

---

# 6. Prompt 怎么处理

换品第一版由用户输入明确的换品提示词。

Skill 不替用户决定换哪个商品、换成什么效果，只附加少量长期稳定的保真约束。

当前结构：

```text
用户换品提示词（必填）
+
Skill 最小保真约束
+
商品图参考角色标记
```

例如换品 Skill：

```text
用户提示词：
把人物手里的旧饮料瓶换成商品图里的新瓶子，Logo 正面朝向镜头
```

Skill 固定补充：

```text
商品图是新商品的唯一外观参考
只替换目标商品
其他人物、动作、镜头、背景、文字和音频尽量不变
```

如果用户没有提供提示词，换品 Skill 不运行，并提示补充。

---

# 7. 一个 Skill 内部可以调用几个模型

没有规定。

一个 Skill 可以：

```text
只调用 1 个模型
```

也可以：

```text
先调用理解模型
↓
再调用生成模型
↓
再调用检查模型
```

但第一原则是：

> 能一个模型解决，就先不要加第二个。

只有真实使用发现效果不够时，再增加步骤。

---

# 8. 第一版换品 Skill 建议结构

第一版使用 Gemini Omni Flash 直接编辑视频：

```text
原视频
+
商品图
+
用户提示词
↓
基础素材检查
↓
上传原视频 + 绑定商品参考图
↓
gemini-omni-flash-preview（task=edit）
↓
下载模型生成的视频
↓
输出视频
```

当前官方边界：

- 输入视频最长 10 秒
- 输出 3–10 秒、720p、24 FPS
- 输出画幅只支持 16:9 或 9:16
- 模型处于预览版
- 模型重新生成视频和音轨，不能承诺原音频逐比特不变

暂时不要主动增加：

- 自动质量检测模型
- 多模型切换
- 自动重试系统
- Agent

除非真实测试证明需要。

产品图片分析与预处理已经由真实输入问题明确提出，因此作为单独的上游辅助 Skill 实现；这里的“自动质量检测模型”仍指视频成片自动评分，不包括产品参考图的必要首检和复检。

# 11. Skill 输入输出标准

虽然第一阶段简单，但三个 Skill 最好保持基本一致。

每个 Skill 都至少应该有：

```text
输入
输出
是否成功
错误信息
运行时间
```

例如：

```json
{
  "success": true,
  "output": "生成结果",
  "error": null
}
```

第一版不需要做得很复杂。

重点是：

> 三个 Skill 不要三个完全不同的风格。

---

# 12. 素材现在怎么处理

第一阶段可以直接使用本地文件。

例如：

```text
D:/素材/video.mp4
D:/素材/product.png
```

这没有问题。

但是尽量避免在代码里写死：

```text
永远只能读取 D:/某个固定目录
```

最好让 Skill 接收文件路径。

这样以后套壳时：

```text
App 上传文件
↓
得到临时文件
↓
继续传给 Skill
```

更容易接起来。

第一阶段不需要提前做云素材库。

---

# 13. 三个 Skill 完成以后再考虑什么

只有下面三件事都发生以后：

```text
换品 Skill 已经稳定
声音克隆 Skill 已经稳定
换口型 Skill 已经稳定
```

再考虑产品化。

那时候再判断：

## 是否做 Workflow

例如：

```text
改文案
↓
声音克隆
↓
换口型
```

如果经常这样组合，就做 Workflow。

## 是否做产品壳

例如前台展示：

```text
视频换品
声音克隆
口播重制
```

后台调用已有 Skill。

## 是否需要 Agent

只有真的出现：

> 用户一句话，需要系统自己判断该调用哪个功能

再考虑 Agent。

不是第一阶段必需品。

---

# 14. 为什么现在不提前做完整架构

因为现在很多东西还不知道。

比如：

- 换品最终最好用哪个模型
- 换品是否真的需要前置理解模型
- 声音克隆会用哪家服务
- 换口型用什么方案稳定
- 三个 Skill 是否真的适合串联
- 用户以后到底最需要哪个产品功能

这些都应该通过真实使用来决定。

---

# 15. 当前最重要的设计原则

> 能简单做出来，就先简单做出来。

同时留一点余地：

```text
API Key 以后能换来源
模型以后能换
Prompt 以后能升级
本地素材以后能接素材库
Skill 以后能被 App 调用
```

但不要现在就把未来全部开发出来。

---

# 16. 项目阶段结构

现在：

```text
WorkBuddy
↓
Skill
↓
模型 API
```

以后可能变成：

```text
素材万象 App
↓
Workflow / Skill
↓
模型 API
```

Skill 是中间最重要的可复用能力。

---

# 17. 一句话总结

> 素材万象第一阶段不是造平台，而是先造 3 个真正好用的电商 AI 工具。  
> 三个工具稳定以后，再决定怎么把它们组合成产品。
